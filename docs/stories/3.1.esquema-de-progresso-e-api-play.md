# Story 3.1 — Esquema de progresso e `/api/play`

**Épico:** 3 – Player próprio (`docs/prd/epic-3-player.md`) · **Status:** InProgress
**Executor:** @data-engineer (schema) + @dev (endpoint) · **Quality gate:** @architect

## História
Como assinante, quero que o sistema saiba onde parei em cada episódio e só me entregue o vídeo quando eu
tiver acesso, para o player (stories seguintes) poder retomar de onde parei com segurança.

## Critérios de aceite
- [x] Tabela `watch_progress` (profile_id, episode_id, position_s, completed, updated_at), uma linha por
      perfil+episódio, RLS (dono vê/grava só o próprio; admin vê tudo).
- [x] `GET /api/play/{episodeId}`: exige login; libera só se o episódio for `is_free = true` **ou** quem
      pede for admin (ver decisão do Épico 3 — checagem de assinatura fica para o Épico 4); devolve
      `{ provider: 'youtube', ref: '<video_ref>' }`.
- [x] Episódio inexistente, não publicado, ou sem acesso → erro (404/403), nunca o `video_ref`.
- [ ] Rate limit em `/api/play` (mesmo padrão já prometido na arquitetura para esta rota). **Reaberto pelo QA
      gate (SEC-003):** a implementação atual deixa um usuário esgotar o limite de outro — corrigir.
- [x] `video_ref` nunca aparece em nenhuma resposta além desta (consistente com a regra já seguida nas
      stories do Épico 2).

## Escopo
- **Dentro:** tabela `watch_progress`, endpoint `/api/play/{episodeId}`.
- **Fora:** o player em si (story 3.2), salvar progresso automaticamente durante a reprodução (story 3.3),
  checagem de assinatura real (Épico 4 — ver decisão no épico).

## Dependências
- Story 2.1 (schema do catálogo) — Done. Usa `episodes`, `titles`.
- Story 1.3 (auth, perfis) — Done. Usa `viewer_profiles`, `is_admin()`.

## Complexidade
- **Média.** Schema pequeno, mas o endpoint precisa decidir qual perfil usar sem um seletor de perfil ainda
  existir no produto (ver Riscos).

## Riscos
- **Sem seletor de perfil ainda:** o produto permite até 4 perfis por conta (FR2), mas nenhuma tela de
  "trocar perfil" existe. Decisão: por enquanto, `watch_progress` usa o primeiro perfil da conta (o mais
  antigo, `created_at`) — mesmo critério que `/conta` já usa para listar perfis. Quando existir seleção de
  perfil, trocar aqui também (fica registrado, não é a solução final).
- **Checagem de assinatura ainda não existe (Épico 4):** `/api/play` libera só gratuito/admin por enquanto —
  decisão já registrada no épico. Importante não deixar essa limitação implícita: o endpoint deve documentar
  isso em comentário, para quem construir o Épico 4 saber que precisa voltar aqui.
- **Rate limit:** mesma dúvida já resolvida na story 1.4 para `/api/events` (limite por sessão, não por IP) —
  usar abordagem equivalente aqui, registrando a mesma limitação conhecida (REQ aberto desde a story 1.4/2.2
  sobre rate limit só por sessão/IP não ser infraestrutura robusta).

## Notas de desenvolvimento

- **Perfil "atual":** `select * from viewer_profiles where account_id = auth.uid() order by created_at limit 1`

- **Controle de acesso ao vídeo:** ver `docs/architecture/index.md`, "Controle de acesso ao vídeo" — o

- **Não implementar aqui:** player, eventos de reprodução, legendas — só o schema e o endpoint.

## Notas de desenvolvimento (implementação)
- **Comentário bem visível no endpoint** (pedido do @po na validação): `src/app/api/play/[episodeId]/route.ts`
  tem um bloco `IMPORTANTE (Épico 4 — Assinaturas...)` logo no topo do arquivo, junto com o mesmo aviso em
  `check_play_access()` no banco — os dois lugares que vão precisar mudar quando `subscriptions` existir.
- **Decisão de design (nova, fora dos critérios de aceite originais):** `check_play_access(episode_id)` é
  uma função SQL própria, não lógica em TypeScript — centraliza a regra de acesso num só lugar (banco), para
  o Épico 4 só precisar mexer ali, sem duplicar a checagem entre o endpoint e outros lugares que vierem a
  precisar da mesma regra.
- **Rate limit por usuário, não por sessão/IP:** tabela dedicada `play_rate_limits` (um registro por
  `user_id`, janela de 1 minuto, limite de 60). Diferente do `/api/events` (story 1.4), aqui sempre há um
  usuário autenticado, então o limite por `user_id` é mais robusto que o de `/api/events` (que é por sessão
  anônima, contornável trocando de sessão) — mas ainda vale o mesmo aviso geral já registrado: um usuário mal-
  intencionado com várias contas poderia multiplicar o limite.
- A leitura do episódio (`select ... from episodes where id = ...`) já usa o cliente normal (respeita RLS da
  story 2.1) — um episódio não publicado ou agendado para o futuro simplesmente não volta para quem não é
  admin, então o endpoint devolve 404 sem precisar duplicar a lógica de visibilidade.

## QA Results

### Review Date: 2026-11-07

### Reviewed By: Quinn (Test Architect)

**CodeRabbit:** não executado — WSL não instalado (fallback do `core-config.yaml`); revisão manual.

**Critérios de aceite:** 4 dos 5 ficam corretos e testados (schema/RLS de `watch_progress`, resposta do
endpoint, 404/video_ref nunca exposto, 401 sem login). O AC de rate limit (AC 4) tem uma falha de segurança
real na implementação.

**Achado:**
- **SEC-003 (high, CONFIRMED):** `check_play_rate_limit(p_user_id uuid)` não confere que `p_user_id` é o
  próprio chamador (`auth.uid()`). Reproduzi com dois usuários reais via `set_config`: um "atacante"
  autenticado chamou a função 61 vezes passando o `uuid` de um "alvo" diferente — a função aceitou
  normalmente, e a vítima (que nunca chamou a função) ficaria com `/api/play` devolvendo 429. Isso quebra o
  padrão que o resto do projeto segue (`ingest_analytics`, `is_admin` etc. sempre usam a identidade do
  próprio chamador) — é um vetor de negação de serviço direto contra qualquer usuário, bastando saber o uuid.

**Não verificado por mim:** fluxo logado no navegador real (mesma lacuna herdada).
