# Story 2.4 — Admin: legendas e traduções

**Épico:** 2 – Catálogo e admin de conteúdo (`docs/prd/epic-2-catalogo-e-admin-de-conteudo.md`) · **Status:** InReview
**Executor:** @dev (+ @data-engineer no T1, bucket de Storage) · **Quality gate:** @architect
**Quality gate tools:** code_review, pattern_validation

## História
Como Gustavo, quero enviar a legenda `.vtt` de cada episódio por idioma, traduzir título/sinopse do episódio,
e gerenciar os gêneros do catálogo, para fechar o cadastro de conteúdo do Épico 2.

## Critérios de aceite
- [x] Na página do episódio (criada na story 2.3), upload de um arquivo `.vtt` por idioma (pt/en/es);
      enviar de novo substitui o arquivo anterior do mesmo episódio+idioma (a tabela `subtitles` da story 2.1
      já impõe um registro por episódio+idioma).
- [x] Arquivo aceito só se terminar em `.vtt` e não passar de 256 KB; erro claro caso contrário.
- [x] Na mesma página, formulário de tradução do episódio (título, sinopse) por idioma — grava em
      `episode_translations` (story 2.1).
- [x] Admin de gêneros (`/admin/generos`): listar, criar, editar e apagar (bloqueado se algum título usa o
      gênero), com nome em pt/en/es (colunas `name_pt`/`name_en`/`name_es` da tabela `genres`).
- [x] Na página de editar título (story 2.2), selecionar quais gêneros se aplicam (grava em `title_genres`).
- [x] Erros de validação aparecem no formulário (arquivo errado/grande demais, nome de gênero obrigatório,
      gênero duplicado).

## Escopo
- **Dentro:** upload de legenda (Supabase Storage), tradução de episódio, CRUD de gêneros, associação
  título↔gênero.
- **Fora:** o player de fato exibir a legenda (Épico 3), página pública de catálogo (Épico 8).

## Complexidade
- **Média.** Primeira vez que o projeto usa Supabase Storage — precisa criar o bucket e as políticas de
  acesso (nenhum bucket existe ainda em nenhuma migration).

## Riscos
- **Bucket de Storage novo:** nada no projeto usa Storage ainda (`docs/architecture/index.md` só cita como
  parte do stack, sem bucket definido). Decisão: bucket `legendas`, leitura pública (o player do Épico 3 vai
  precisar buscar o `.vtt` direto do navegador), escrita só admin — via política de Storage usando
  `is_admin()`, mesmo padrão das tabelas. Registrar essa decisão para o @architect confirmar.
- **Apagar gênero em uso:** `title_genres` tem FK `on delete cascade` para `genres` — apagar um gênero usado
  apagaria a associação em silêncio. O AC pede bloquear a exclusão nesse caso (igual ao risco de apagar
  temporada com episódios, story 2.2) — checar no servidor antes de apagar, não confiar só no cascade.
- **Tamanho/tipo do arquivo `.vtt`:** validar no servidor (o `Content-Type` do navegador para `.vtt` nem
  sempre é confiável) — conferir a extensão do nome do arquivo e o tamanho antes de enviar ao Storage.

## Notas de desenvolvimento
- **Padrões a reaproveitar:** `requireAdmin` (`src/lib/supabase/admin.ts`), Server Action + `useActionState`
  (`title-form.tsx`/`actions.ts`, `episode-form.tsx`/`episode-actions.ts`), `src/lib/datetime-local.ts` se
  algum campo de data entrar aqui (não deveria — esta story não tem agendamento).
- **Cliente de Storage:** usar o mesmo `createClient()` de `src/lib/supabase/server.ts` — o client do
  `@supabase/ssr` já expõe `.storage`. Não criar um cliente novo.
- **Upload sempre substitui:** como `subtitles` tem `unique(episode_id, locale)` (story 2.1), o Server Action
  deve apagar/sobrescrever o arquivo antigo no Storage (ou usar `upsert: true` do Storage) ao enviar de novo
  para o mesmo episódio+idioma — não deixar arquivos órfãos acumulando no bucket.
- **Não inventar:** nenhum campo além de `subtitles.url`, `episode_translations.{title,synopsis}`,
  `genres.{name_pt,name_en,name_es}`, `title_genres` — já todos no schema da story 2.1.

## Notas de desenvolvimento (implementação)
- **Bucket `legendas`:** `public: true`, `file_size_limit: 262144` (256 KB, igual ao limite validado no
  app), `allowed_mime_types: ['text/vtt','text/plain']` — limite também imposto pelo próprio Storage, não só
  pelo código do servidor. Políticas de `storage.objects` seguem o mesmo padrão de `is_admin()` das tabelas.
- **Caminho do arquivo:** `{episode_id}/{locale}.vtt` — fixo por episódio+idioma, então `upload(..., {upsert:
  true})` sempre sobrescreve o arquivo anterior no mesmo caminho; não sobram arquivos órfãos no bucket.
- **Apagar gênero em uso:** checagem de `count` em `title_genres` antes do `delete`, mesmo padrão de
  `deleteSeason` (story 2.2) — não é um constraint do banco (a FK é `on delete cascade`), então a garantia é
  só na Server Action. Fica a mesma corrida já aceita em `deleteSeason`: duas exclusões simultâneas do mesmo
  gênero não travam uma a outra (risco baixo, ferramenta de uso único pelo Gustavo).
- **Gêneros do título:** `saveTitleGenres` apaga todas as linhas de `title_genres` do título e reinsere as
  selecionadas — simples, mas significa que cada salvamento é uma substituição completa, não um diff.
