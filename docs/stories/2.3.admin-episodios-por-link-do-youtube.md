# Story 2.3 — Admin: episódios por link do YouTube

**Épico:** 2 – Catálogo e admin de conteúdo (`docs/prd/epic-2-catalogo-e-admin-de-conteudo.md`) · **Status:** InReview
**Executor:** @dev · **Quality gate:** @architect · **Quality gate tools:** code_review, pattern_validation, security_check

## História
Como Gustavo, quero cadastrar um episódio colando o link do YouTube, marcando onde começam e terminam a
abertura e os créditos, para publicar capítulos sem mexer em código nem SQL.

## Critérios de aceite
- [x] Série: dentro de uma temporada (`/admin/titulos/{id}/temporadas/{seasonId}`), lista de episódios com
      link para criar e para editar cada um.
- [x] Filme: a página do título (story 2.2) ganha uma seção "Vídeo" com o único episódio do filme — criar se
      ainda não existe, editar se já existe (um filme tem no máximo 1 episódio, regra já no banco desde a story 2.1).
- [x] Formulário de episódio aceita um link do YouTube em formatos comuns (`watch?v=`, `youtu.be/`, `embed/`)
      ou o ID puro, e extrai o ID (`video_ref`) sozinho; erro claro se não reconhecer o link.
- [x] Campos do formulário: número (série; sugerido automaticamente, editável), duração em segundos (manual —
      ver Dev Notes sobre preenchimento automático), início/fim da abertura, início dos créditos, gratuito,
      status (`draft`/`scheduled`/`published`), data de agendamento.
- [x] Erros de validação aparecem no formulário (link não reconhecido, número de episódio duplicado na
      temporada, campos obrigatórios).
- [x] `video_ref` nunca aparece fora do admin (não há página pública nesta story — Épico 8/3 cuidam disso
      depois; conferir que nada novo nesta story expõe o ID fora de `/admin`).

## Escopo
- **Dentro:** CRUD de episódio (série dentro de temporada; filme como vídeo único do título), parser de link
  do YouTube, marcações de tempo (abertura/créditos), gratuito, status/agendamento.
- **Fora:** traduções de episódio e legendas (story 2.4), preenchimento automático de duração via API do
  YouTube (sem chave configurada — ver Dev Notes), páginas públicas e o player em si (Épicos 3 e 8).

## Dependências
- Story 2.2 (admin de títulos e temporadas) — Done. Reaproveita o layout do admin, `requireAdmin`, e o padrão
  de Server Action + `useActionState` do formulário de título.
- Story 2.1 (schema do catálogo) — Done. Usa `episodes` (com a dupla via `season_id`/`title_id` da story 2.1)
  e os índices únicos que já impedem dois episódios no mesmo número de temporada ou mais de um por filme.

## Complexidade
- **Média.** Duas entradas para o mesmo formulário (série via temporada, filme via título), parser de link,
  mais validação de duplicidade de número.

## Riscos
- **Preenchimento automático de duração:** o critério "preenche duração quando possível" do Épico 2 precisa de
  uma forma de consultar o YouTube (API de Dados v3 com chave, ou scraping, nenhum dos dois configurado hoje).
  Decisão: duração fica **manual** nesta story; automatizar é trabalho futuro que depende de uma chave de API
  (pendência do Gustavo, como o Google OAuth da story 1.3), não inventar a integração sem a chave existir.
- **Formatos de link do YouTube variam bastante** (com/sem `www`, `m.`, parâmetros extras como `&t=30s`,
  `youtube-nocookie.com`, Shorts) — o parser precisa cobrir os formatos comuns sem tentar adivinhar todos.
- **Filme com episódio único:** a UI precisa diferenciar "criar" (ainda não existe) de "editar" (já existe)
  no mesmo lugar da tela, sem deixar criar um segundo (o índice único do banco já impede, mas a UI deve evitar
  mostrar "criar" quando já existe).

## Notas de desenvolvimento
- **Reaproveitar os padrões da story 2.2:** `requireAdmin` (`src/lib/supabase/admin.ts`), Server Action +
  `useActionState` (`title-form.tsx`/`actions.ts` como referência), `Input`/`Button` de `src/components/ui/`.
- **`EpisodeForm` único para os dois casos (série/filme):** receber `parentKind: "season" | "movie"` e o id
  correspondente (`season_id` ou `title_id`); o Server Action decide qual coluna preencher.
- **Duração manual por enquanto:** não implementar chamada à API do YouTube nesta story — não há
  `YOUTUBE_API_KEY` configurada em `web/.env.example` nem em nenhum lugar do projeto. Se o Gustavo quiser
  automatizar, é um adendo futuro (como o Google OAuth pendente da story 1.3).
- **Parser do link:** aceitar também o ID puro colado direto (11 caracteres), para quando o Gustavo já tiver
  só o ID à mão. Regex de validação do ID: `^[A-Za-z0-9_-]{11}$` (padrão de IDs de vídeo do YouTube).
- **Número do episódio:** mesmo padrão de "sugerir o próximo" usado em `createSeason` (story 2.2) — calcular
  o maior número existente na temporada +1, mas deixar o campo editável (não travado), já que o formulário de
  criar/editar episódio é mais provável de precisar reordenar do que o de temporada.
- **Importante (Constitution, Artigo IV — No Invention):** não adicionar nenhum campo além do schema da
  story 2.1 (`episodes`) e destes critérios de aceite — em especial, nenhum campo de tradução/legenda aqui
  (isso é a story 2.4).
- **Campo "Agendar para" (`release_at`):** a story 2.2 tem um achado de QA aberto (REL-001, gate
  `docs/qa/gates/2.2-admin-titulos-e-temporadas.yml`) — preencher um `<input type="datetime-local">` com um
  corte cru do timestamp UTC do banco, sem converter para o horário local do navegador, desloca o valor a
  cada edição. **Não copiar esse trecho de `title-form.tsx`**: implementar a conversão certa aqui (converter
  UTC → horário local do navegador ao preencher o campo, e local → UTC explícito ao enviar), e, se der tempo,
  aplicar a mesma correção de volta em `title-form.tsx` como parte desta story (fora do escopo formal, mas é
  o mesmo bug e o mesmo arquivo de padrão).
